================================================================================
FILESTACK DEMO-APP PROMPT LIBRARY
300 build prompts across 10 verticals
================================================================================

Each prompt is a complete build brief for one demo application in the
fileschool monorepo, in the shape of the apps already in apps/: a Next.js 16
app where Filestack replaces an entire processing tier, plus the ARTICLE.md
that explains what was deleted.

HOW TO USE ONE
  1. Copy a single prompt block, from its PROMPT header to its ARTICLE line.
  2. Hand it to a coding agent from the repo root, or use it as the spec for a
     hand-built app.
  3. The STACK line is deliberately near-identical in every prompt. That is the
     monorepo contract, not filler. Everything else is the concept.

THE CONTRACT EVERY PROMPT INHERITS
  - Next.js 16 (App Router, Server Actions), TypeScript strict, Tailwind v4,
    React 19. Read node_modules/next/dist/docs/ before writing code — this
    Next.js version has breaking changes.
  - libSQL for data: a local SQLite file in dev, Turso when TURSO_DATABASE_URL
    is set, one code path for both. Seed on first run.
  - Filestack does all upload, storage, delivery and processing. No image,
    video, PDF or OCR processing code in the repo. No /api/upload route —
    bytes go browser to Filestack, metadata rides in on the Server Action.
  - filestack-js loaded by lazy dynamic import, client memoised at module
    level, NEXT_PUBLIC_FILESTACK_API_KEY read on the client.
  - Degrade, never explode: with no API key the app still runs and the pickers
    render a "set your key" hint.
  - CONTRIBUTING.md conventions: components/features/, forms/, modals/,
    interfaces/ with the I prefix, Zustand in store/, named exports, files
    under 200 lines.
  - Ship it looking finished: real empty states, skeletons, keyboard support,
    visible focus rings, a designed dark mode, no lorem ipsum.

Vertical context — buyers, constraints, design direction, Filestack surface —
is in verticals.txt alongside this file.

PROMPT 001 · EDUCATION · Rubric Room
app slug: apps/fs-edu-rubric-room
────────────────────────────────────────────────────────────────────────────────

PROBLEM. A grade out of 100 tells a student nothing. Rubrics were invented to
fix that, and then got buried in spreadsheets that nobody links back to the
actual work. The marker knows exactly which paragraph failed the "evidence"
criterion, but the tooling gives them a dropdown and a comment box, so the
connection between the mark and the page is lost the moment it is made.

BUILD. A rubric-driven marking desk. A lecturer defines a rubric — criteria,
level descriptors, weights — and attaches it to an assignment. Students submit
work as photos, scans, PDFs or documents. When the lecturer opens a submission,
the rubric sits in a rail beside the rendered page, and selecting a criterion
puts the canvas into anchor mode: any mark they draw is bound to that criterion.
The final grade is computed from the rubric, and the student sees each criterion
score with a "show me where" button that jumps to the exact region of the exact
page that earned it.

ROLES.
  - Lecturer — builds rubrics, marks submissions, anchors evidence to criteria.
  - Student — submits work, reads criterion-by-criterion feedback with evidence.
  - Course lead — reuses rubric templates across assignments.

SCREENS.
  - Rubric builder with live weight totals and level descriptors.
  - Assignment list with submission counts and marking progress.
  - Marking canvas: rendered page, criterion rail, anchored annotation tools.
  - Student result view with per-criterion scores and jump-to-evidence.
  - Rubric template library.

CENTREPIECE. The anchor-mode canvas. Selecting "Use of evidence" tints the
toolbar, and every box drawn while it is active becomes a citation for that
criterion. The student's result page then reverses it: click a criterion, the
page scrolls and the region pulses. Marking and feedback become the same act.

FILESTACK.
  - Picker with local, url, googledrive, dropbox and onedrive sources for
    submissions.
  - `pdfinfo` for page counts, `output=format:png,page:N,density:150` to render
    any page of a PDF submission on demand.
  - `resize=width:1600,fit:max` for the canvas, `fit:crop` for thumbnails.
  - Annotation overlays pushed up with `client.upload` as transparent PNGs —
    one overlay per criterion so they can be toggled independently.
  - `cache=expiry:max` on download URLs.

DATA. course; assignment; rubric; criterion; submission; annotation (with
criterion_id, page, overlay handle); criterion_score.

STACK. Next.js 16 App Router with Server Actions for every mutation, TypeScript
strict, Tailwind v4, libSQL/Turso, Zustand for canvas tool state only. No
upload route. Seed with two courses, one rubric and four submissions.

EDGE CASES.
  - A rubric is edited after marking has begun — existing scores must not
    silently change.
  - A submission is four JPEGs of printed pages in the wrong order.
  - Overlays for eight criteria on one page must not fight for z-order.
  - A student resubmits after partial marking.

DONE WHEN.
  - A lecturer can mark a 6-page PDF criterion by criterion without the page
    ever leaving the browser.
  - The student result view jumps to the annotated region for every criterion.
  - The original submission file is byte-identical to what was uploaded.
  - Weights always total 100 and the UI refuses to save when they do not.

ARTICLE. Rubrics fail because the mark is divorced from the page. Here the
overlay is per-criterion, and the "why" is one URL away.

PROMPT 002 · EDUCATION · Lab Notebook
app slug: apps/fs-edu-lab-notebook
────────────────────────────────────────────────────────────────────────────────

PROBLEM. Science coursework is evidence coursework. A student runs a titration,
photographs the burette, records the colour change, and writes it up — and the
lab report becomes a Word document with pasted images at 4MB each, emailed to a
demonstrator who cannot tell whether the photo was taken during the session or
copied from a friend. The evidence and the write-up live in different places
and neither proves anything about the other.

BUILD. A structured lab notebook where each experiment is a sequence of steps,
and each step accepts typed observations plus photo or video evidence captured
in the session. Entries are timestamped and locked once submitted. The
demonstrator reviews a report as a timeline: step, observation, evidence
thumbnail, capture time, with a flag when a photo's EXIF timestamp falls
outside the booked session window. Reports export as a single ordered document.

ROLES.
  - Student — works through the protocol, captures evidence per step.
  - Demonstrator — reviews timelines, flags anomalies, marks the report.
  - Technician — publishes protocols and session windows.

SCREENS.
  - Protocol library with session windows and equipment lists.
  - Live notebook: step-by-step capture with a persistent camera button.
  - Report timeline for review, with EXIF flags inline.
  - Marking view with per-step comments.
  - Export view producing an ordered bundle.

CENTREPIECE. The evidence timeline. Every step is a row: what the protocol
asked, what the student wrote, what they photographed, and when the camera says
they photographed it. Mismatches between session window and capture time are
shown as an honest, explainable flag — never an accusation.

FILESTACK.
  - Picker with webcam and mobile capture so evidence is taken in the lab, not
    remembered afterwards.
  - `exif` to read capture timestamp and device off each photo.
  - `resize=width:1200,fit:max` for the timeline, `fit:crop` squares for rows.
  - `output=format:webp` + `quality` so a 30-step report still loads on campus
    Wi-Fi.
  - `zip` to export the full evidence set with the report.

DATA. protocol; step; session; notebook_entry; evidence_item (handle, exif
timestamp, device); review_comment; report_export.

STACK. Next.js 16 App Router, Server Actions, TypeScript, Tailwind v4,
libSQL/Turso. filestack-js lazily imported; EXIF read through the CDN task, not
a client-side parser. Seed with one full worked experiment.

EDGE CASES.
  - A photo has no EXIF because it came through a messaging app.
  - The student captures evidence offline and it uploads twenty minutes later.
  - A step is completed out of order.
  - A video of a reaction is 400MB and must preview without downloading.

DONE WHEN.
  - A full experiment can be captured on a phone, one step at a time.
  - The timeline shows capture time for every item and says so plainly when it
    is missing.
  - A submitted report is immutable and the export reproduces it exactly.
  - The demonstrator can mark without downloading anything.

ARTICLE. Provenance for coursework evidence, with no metadata parser in the
repo — `exif` is a URL task and the honest flag is four lines of logic.

PROMPT 003 · EDUCATION · Crit Board
app slug: apps/fs-edu-crit-board
────────────────────────────────────────────────────────────────────────────────

PROBLEM. Art and design education runs on the crit: work pinned to a wall,
everyone standing around it, comments landing on specific parts of specific
pieces. Move that online and it becomes a video call where six people describe
the top-left corner in words. The spatial, comparative nature of a crit — this
one next to that one, this detail versus that detail — is exactly what
general-purpose tools destroy.

BUILD. A digital crit wall. A tutor creates a crit session and students pin
work to it: images, PDFs of layouts, photographs of physical models. The wall is
a zoomable board where pieces can be arranged, grouped and compared side by
side. Anyone in the session can drop a pin comment on a precise point of a
precise piece. Comments thread, resolve, and are exportable as a feedback sheet
per student.

ROLES.
  - Tutor — creates sessions, arranges the wall, leads the crit.
  - Student — pins work, comments on peers, reads their own feedback sheet.
  - Visiting critic — comment-only access via a share link.

SCREENS.
  - Crit wall: zoomable, pannable board of pinned work.
  - Piece detail with full-resolution zoom and pin comments.
  - Compare mode: two or four pieces locked side by side.
  - Per-student feedback sheet.
  - Session setup and invite links.

CENTREPIECE. Compare mode. Select two pieces and they lock into a split view
with synchronised zoom, so a tutor can pull up the same detail on both at once.
The zoom is served straight from the handle at the resolution needed, so a
2400px crop appears instantly without ever having loaded the full original.

FILESTACK.
  - Picker with `transformations: { crop, rotate }` so students straighten a
    photographed model before pinning it.
  - A resolution ladder from one handle: `resize=width:320` for the board,
    `width:1200` for detail, `width:2400` for zoom.
  - `output=format:png,page:N` so a multi-page layout PDF pins as pages.
  - `output=format:webp` + `quality:82` for board tiles.
  - Pin comments stored as coordinates, never burned into the image.

DATA. crit_session; piece (handle, mimetype, board position); pin_comment
(piece_id, x, y, thread); participant; feedback_sheet.

STACK. Next.js 16 App Router, Server Actions, Tailwind v4, Zustand for board
viewport and selection state, libSQL/Turso. Board transforms are CSS, image
resolution comes from the CDN. Seed with a populated wall of eight pieces.

EDGE CASES.
  - Forty pieces on one wall must not load forty full-resolution images.
  - A photographed model is shot at an angle and needs rotation before pinning.
  - Two people comment on the same point simultaneously.
  - A visiting critic opens the link with no account.

DONE WHEN.
  - The board scrolls and zooms smoothly with forty pieces pinned.
  - Compare mode keeps two pieces in synchronised zoom.
  - Every pin comment resolves to an exact coordinate on an exact piece.
  - Feedback sheets export per student with the pinned context intact.

ARTICLE. A zoomable comparison wall is a tiling and resolution problem. One
handle plus a width parameter is the entire tiling strategy.

PROMPT 004 · EDUCATION · Blind Peer Review
app slug: apps/fs-edu-peer-review
────────────────────────────────────────────────────────────────────────────────

PROBLEM. Peer review teaches more than marking does, and almost nobody runs it
properly because the logistics are brutal: collect the work, strip the names,
distribute it so nobody reviews their friend, collect the reviews, strip those
names too, return them, and make sure the student who wrote "good job" gets
told that is not a review. Every step is a place for a name to leak.

BUILD. An anonymised peer review round. Students submit work; the system
allocates each submission to N reviewers with no overlap and no self-review;
reviewers see the work with identifying regions masked and complete a structured
review form with inline annotations. Authors receive aggregated, anonymised
feedback. The tutor sees everything, plus a review-quality score so lazy reviews
are visible.

ROLES.
  - Student author — submits, later reads aggregated anonymous feedback.
  - Student reviewer — reviews allocated work under anonymity.
  - Tutor — configures the round, sees the unmasked truth, grades reviews.

SCREENS.
  - Round setup: deadlines, reviewers per submission, review form builder.
  - Reviewer queue with allocated work.
  - Review canvas: masked page render, structured form, inline annotations.
  - Author feedback view, aggregated and anonymised.
  - Tutor overview with allocation map and review-quality scores.

CENTREPIECE. The masking layer. A submission's name block is masked server-side
before the reviewer ever receives a URL — the render they get is a transformed
image with the identifying region obscured, not a full image with CSS over the
top. The tutor can toggle the unmasked view; the reviewer has no path to it.

FILESTACK.
  - `output=format:png,page:N` to render submission pages for review.
  - `partial_pixelate` over the declared name region so masking is baked into
    the delivered image.
  - Signed Security Policies so a reviewer cannot hand-edit a URL into the
    unmasked original.
  - Annotation overlays uploaded via `client.upload`, one per reviewer.
  - `resize` presets for queue thumbnails.

DATA. round; submission; allocation; review; review_annotation; mask_region;
review_quality_score.

STACK. Next.js 16 App Router, Server Actions, TypeScript, Tailwind v4,
libSQL/Turso. All URL construction for masked renders happens server-side.
Seed with a completed round so the aggregate view has something in it.

EDGE CASES.
  - A student writes their name inside the body text, not the header.
  - An odd number of submissions makes clean allocation impossible.
  - A reviewer misses the deadline and the round must still close.
  - A reviewer submits a one-word review.

DONE WHEN.
  - No reviewer-facing URL can be manipulated into an unmasked render.
  - Allocation never assigns a student their own work.
  - Authors see aggregated feedback with no reviewer identity anywhere.
  - The tutor can see and grade every review.

ARTICLE. Anonymity that survives DevTools. The mask is in the transformation,
so the unmasked bytes are never delivered in the first place.

PROMPT 005 · EDUCATION · Worksheet Snap
app slug: apps/fs-edu-worksheet-snap
────────────────────────────────────────────────────────────────────────────────

PROBLEM. Primary and secondary homework is paper. The teacher hands out a
worksheet, the child does it at the kitchen table, and the parent photographs it
at 9pm at an angle, in artificial light, with the edge of a plate in frame. The
teacher then opens thirty of those on a Sunday, each one rotated differently,
half of them too dark to read.

BUILD. A homework capture app built for parents and children, where the capture
step does the work. The child or parent photographs the sheet; the app
straightens, crops to the page, brightens it and shows the cleaned result before
submission, with a retake option. The teacher gets a uniform grid of readable,
identically-framed pages, can tick them off in a keyboard-driven flow, and can
draw a tick, a star or a short note on any of them.

ROLES.
  - Parent or pupil — photographs homework, checks the cleaned preview, submits.
  - Teacher — reviews a uniform grid, marks quickly, sends stickers and notes.
  - Head of year — sees completion rates per class.

SCREENS.
  - Capture flow: camera, auto-clean preview, retake or submit.
  - Pupil homework history with teacher stickers.
  - Teacher grid view, one class, one assignment, keyboard-driven.
  - Quick-mark canvas with tick, star, circle and note tools.
  - Class completion dashboard.

CENTREPIECE. The clean-up preview. Between shutter and submit, the app shows
the corrected page — deskewed, cropped, brightened — beside a "retake" button.
Parents submit something legible because they can see it is legible, and the
teacher's Sunday stops being an exercise in squinting.

FILESTACK.
  - Picker with webcam and mobile capture, `transformations: { crop, rotate }`
    exposed to the parent for the manual case.
  - `enhance` and `modulate` for brightness and contrast recovery on dark
    kitchen-table photos.
  - `rotate` applied from the chosen orientation.
  - `resize=width:1400,fit:max` for the marking canvas, `fit:crop` for the grid.
  - `sfw` on parent-submitted images as a basic safety gate.

DATA. class; pupil; assignment; capture (original handle, applied transform
chain); mark; sticker; completion_record.

STACK. Next.js 16 App Router, Server Actions, Tailwind v4, libSQL/Turso. The
transform chain is stored as a string and re-applied at render — the original
photo is never replaced. Mobile-first layout, large tap targets throughout.

EDGE CASES.
  - The photo is taken in portrait but the sheet is landscape.
  - A parent submits a photo of the wrong worksheet.
  - Two children in one household share a device.
  - The photo is 18MB straight off a modern phone.

DONE WHEN.
  - Capture-to-submit works one-handed on a phone in under twenty seconds.
  - The teacher grid shows thirty uniformly framed, readable pages.
  - Marking thirty pieces is possible without the mouse.
  - The original photo remains retrievable and unmodified.

ARTICLE. Image clean-up as a UX problem, not a CV problem. Deskew, crop and
brighten are a chain of URL tasks the parent approves before submitting.

PROMPT 006 · EDUCATION · Thesis Desk
app slug: apps/fs-edu-thesis-desk
────────────────────────────────────────────────────────────────────────────────

PROBLEM. A dissertation is written over a year in twenty drafts, each one
emailed to a supervisor as "chapter3_v4_FINAL_revised.docx". Supervisor comments
live in tracked changes in whichever copy they replied to. Nobody can answer the
only question that matters at the viva: what changed between draft five and
draft six, and did the student act on the feedback?

BUILD. A supervision desk built around chapter versions. Students upload each
draft; every version is retained, rendered page by page and diffed against its
predecessor at the page level. Supervisors comment on specific pages of specific
versions. Every comment carries a state — open, addressed, or dismissed with a
reason — and the student's next upload prompts them to link each new version to
the comments it answers.

ROLES.
  - Postgraduate student — uploads drafts, links revisions to feedback.
  - Supervisor — reads versions, comments on pages, tracks open threads.
  - Examiner — reads the final version with the supervision history attached.

SCREENS.
  - Chapter timeline: every version with date, page count and comment counts.
  - Version reader with page navigation and margin comments.
  - Side-by-side version comparison.
  - Open-threads dashboard across all chapters.
  - Submission bundle assembly.

CENTREPIECE. The version comparison. Two drafts, page thumbnails rails on both
sides, scroll-locked, with pages the student has flagged as changed highlighted.
Supervisors stop reading a whole chapter again to find three altered paragraphs.

FILESTACK.
  - Picker accepting PDF and DOCX from local, Drive and OneDrive.
  - `output=format:pdf` to normalise DOCX drafts into one readable format.
  - `pdfinfo` for page counts per version.
  - `output=format:png,page:N,density:150` to render pages on demand for both
    the reader and the comparison rails.
  - `zip` to assemble the final submission bundle with supervision history.

DATA. thesis; chapter; version (handle, page_count, uploaded_at); page_comment
(version_id, page, state); revision_link; submission_bundle.

STACK. Next.js 16 App Router, Server Actions, TypeScript, Tailwind v4,
libSQL/Turso. Versions are append-only; nothing is ever overwritten. Seed with
a chapter at version four with a realistic comment history.

EDGE CASES.
  - A 180-page thesis must paginate without loading 180 renders.
  - A DOCX and a PDF version of the same draft are both uploaded.
  - A comment refers to a page that no longer exists in the next version.
  - A supervisor comments while the student is uploading a new version.

DONE WHEN.
  - Every version ever uploaded is still readable, page by page.
  - Comparison view scroll-locks two versions with synchronised page numbers.
  - Every comment has an explicit state and an audit of who changed it.
  - The final bundle contains the thesis and its full supervision history.

ARTICLE. Version-aware document review with no document conversion service:
DOCX to PDF to page images is one chain, on demand, per page.

PROMPT 007 · EDUCATION · Script Splitter
app slug: apps/fs-edu-script-splitter
────────────────────────────────────────────────────────────────────────────────

PROBLEM. Exam season: two hundred scripts go through a departmental scanner and
come out as four enormous PDFs. Somebody now has to work out where each
student's script starts and ends, split them, match them to candidate numbers,
and distribute them to markers by question. This is done by hand, at night, by
whoever is most junior, and a mis-split ruins a candidate's day.

BUILD. A bulk script intake tool. Upload the scanner's output, render every page
as a thumbnail, and let an administrator define script boundaries on a single
scrolling page-strip — click the first page of each script, and the boundaries
snap. Candidate numbers are read off the cover pages automatically and shown for
confirmation. Split scripts are then allocated to markers by question, and each
marker sees only their pages.

ROLES.
  - Exams administrator — uploads scans, sets boundaries, confirms candidates.
  - Marker — marks allocated questions across many scripts.
  - Chief examiner — monitors progress and samples marked work.

SCREENS.
  - Batch upload with per-file page counts.
  - Page-strip splitter: every page as a thumbnail with boundary markers.
  - Candidate confirmation queue with OCR suggestions.
  - Marker queue, one question at a time across scripts.
  - Progress dashboard by question and marker.

CENTREPIECE. The page strip. Hundreds of page thumbnails in one horizontal
scroller, each rendered straight from the source PDF at thumbnail size, with
boundary handles that can be dragged. Splitting two hundred scripts becomes a
five-minute task in one view rather than a filesystem exercise.

FILESTACK.
  - `pdfinfo` to get the page count of each scanner output.
  - `output=format:png,page:N,density:72` + `resize=width:180` for the strip.
  - `output=format:png,page:N,density:150` for marking-resolution pages.
  - `ocr` on cover pages to read candidate numbers.
  - `zip` to export a marked cohort for the exam board.

DATA. exam; scan_batch; page (source handle, page index); script (page range,
candidate number, confidence); allocation; mark; sample_check.

STACK. Next.js 16 App Router, Server Actions, TypeScript, Tailwind v4,
libSQL/Turso. Scripts are page ranges over a source handle — no file is ever
physically split or re-uploaded. Seed with a 40-page batch of six scripts.

EDGE CASES.
  - A candidate number is handwritten and OCR guesses wrong.
  - A script has a blank page in the middle that must not end it.
  - Pages are scanned upside down for one script.
  - Two administrators split the same batch at once.

DONE WHEN.
  - A 200-page batch renders as a scrollable strip without stalling.
  - Splitting is done entirely by page ranges, with no re-upload.
  - Every candidate number is either OCR-confirmed or human-confirmed.
  - A marker only ever sees the pages allocated to them.

ARTICLE. "Splitting" a PDF without splitting anything: a script is a page range
and a handle, and the pages are rendered on demand.

PROMPT 008 · EDUCATION · Language Lab
app slug: apps/fs-edu-language-lab
────────────────────────────────────────────────────────────────────────────────

PROBLEM. Language learning needs speaking practice, and speaking practice needs
a teacher to hear it. Learners record on their phones and send voice notes in
whatever format the phone chose, in wildly different volumes, and the teacher's
feedback — "your stress is on the wrong syllable at 0:14" — arrives as a text
message with no way to hear the moment being described.

BUILD. An asynchronous speaking lab. A teacher publishes a prompt with a model
recording. Learners record a response in the browser or upload one. The teacher
opens a submission and gets a waveform with timestamped comment pins: click at
0:14, leave a note, optionally record a corrected pronunciation right there. The
learner plays their own recording and hears the teacher's correction at exactly
the point it applies.

ROLES.
  - Teacher — publishes prompts, leaves timestamped audio and text feedback.
  - Learner — records responses, listens to feedback in context.
  - Course coordinator — tracks speaking practice minutes per learner.

SCREENS.
  - Prompt list with model recordings.
  - Recording screen with waveform, retake and submit.
  - Teacher review with waveform and pin comments.
  - Learner playback with feedback pins on the timeline.
  - Practice minutes dashboard.

CENTREPIECE. The pinned waveform. Both sides of the conversation share one
timeline: the learner's recording with the teacher's notes and micro-recordings
attached to the exact second they refer to. Feedback stops being a description
of a moment and becomes the moment.

FILESTACK.
  - Picker with audio recording enabled, plus file upload for learners who
    recorded elsewhere.
  - `audio_convert` to normalise every submission to one web-playable format
    and consistent loudness.
  - Teacher correction clips uploaded with `client.upload` as separate handles.
  - `virus_detection` on uploaded files from outside the browser recorder.
  - Short-expiry signed policies on learner recordings.

DATA. prompt; model_recording; submission (handle, duration); feedback_pin
(timestamp, note, optional clip handle); practice_log.

STACK. Next.js 16 App Router, Server Actions, Tailwind v4, libSQL/Turso.
Waveform rendered from the audio element in the browser; no audio processing
library in the repo. Zustand holds player state only.

EDGE CASES.
  - A learner uploads an M4A the browser will not play natively.
  - A recording is 40 minutes when it should be 40 seconds.
  - Two feedback pins land on the same second.
  - A learner records with the microphone muted and submits silence.

DONE WHEN.
  - Any submitted audio format plays back in every modern browser.
  - Feedback pins are accurate to the second on both sides.
  - The teacher can record a correction without leaving the review screen.
  - Silent or empty recordings are detected and flagged before submission.

ARTICLE. Audio normalisation across whatever a phone decided to record, with no
ffmpeg in the repository.

PROMPT 009 · EDUCATION · Course Pack Builder
app slug: apps/fs-edu-course-pack
────────────────────────────────────────────────────────────────────────────────

PROBLEM. Every module has a reading pack: chapters, papers, handouts, past
exams, assembled into one document with a cover sheet and a copyright notice.
It is rebuilt every year by hand, in Word, from a folder of PDFs of varying
quality, and the copyright declaration that legally must appear on each extract
is added manually or forgotten entirely.

BUILD. A course pack assembler. Librarians and lecturers add sources — PDFs,
scans, images, DOCX handouts — select page ranges from each, order them by drag,
and generate a pack. Every extract automatically carries a stamped copyright
declaration. Packs are versioned per academic year, and students access them
through expiring links rather than a permanent public file.

ROLES.
  - Lecturer — chooses readings and page ranges, orders the pack.
  - Librarian — checks licensing, approves extracts, applies declarations.
  - Student — reads the pack in the browser, downloads if permitted.

SCREENS.
  - Source library with page-level previews.
  - Extract picker: choose page ranges visually from a page strip.
  - Pack composer with drag-ordered sections and running page count.
  - Licensing review queue for the librarian.
  - Student reader with page navigation.

CENTREPIECE. The extract picker. Pick a source, see its pages as thumbnails,
drag a range, and it enters the pack as a section — with the copyright stamp
already visible on the preview. What the librarian approves is exactly what the
student receives.

FILESTACK.
  - `pdfinfo` per source for page counts, `output=format:png,page:N` for the
    page strip.
  - `output=format:pdf` to bring DOCX handouts into the pack format.
  - `watermark` to stamp the copyright declaration onto every extracted page.
  - `zip` for a downloadable pack where licensing allows it.
  - Security Policies with academic-year expiry on student access URLs.

DATA. module; source (handle, page_count, licence); extract (source_id, page
range); pack; pack_version; access_grant.

PROBLEM. Physiotherapy works if the home exercises are done correctly, and the
therapist has no idea whether they are. Patients are given a paper sheet of
stick figures, do the exercise wrong for three weeks, and return no better. The
feedback loop between the clinic and the living room does not exist.

BUILD. A home exercise programme with video check-ins. Therapists build a
programme from a library of demonstration videos, with reps, sets and cues.
Patients record themselves performing the exercise; the therapist reviews with
side-by-side playback — demonstration on the left, patient on the right, both
scrubbing together — and leaves timestamped cues. Progress is tracked by
adherence and by range-of-motion comparison across weeks.

ROLES.
  - Physiotherapist — builds programmes and reviews patient check-in videos.
  - Patient — follows the programme, records check-ins on a phone.
  - Clinic lead — monitors adherence and outcomes across caseloads.

SCREENS.
  - Programme builder from the exercise library.
  - Patient programme view with demonstration video and record button.
  - Side-by-side review player with synchronised scrubbing.
  - Timestamped cue feedback for the patient.
  - Adherence and progress dashboard.

CENTREPIECE. Synchronised side-by-side playback. Demonstration and patient
video scrub together, so a therapist can show the difference at the exact point
in the movement where it goes wrong — and the patient sees the same pairing when
they watch the feedback.

FILESTACK.
  - Picker with video recording and mobile capture, background upload enabled.
  - `video_convert` to normalise phone recordings into a web rendition.
  - Poster frames for check-in thumbnails.
  - Freeze-frame annotation overlays uploaded via `client.upload`.
  - Short-expiry signed policies — these are videos of patients' bodies.

DATA. programme; exercise; demonstration_video; check_in (handle, rendition,
recorded_at); cue (timestamp, note); adherence_record; progress_measure.

STACK. Next.js 16 App Router, Server Actions, TypeScript, Tailwind v4,
libSQL/Turso. Zustand for the dual-player sync state. Mobile-first for the
patient. Seed with a four-week programme and check-ins.

EDGE CASES.
  - A patient records in portrait while the demonstration is landscape.
  - A check-in video is recorded at 60fps and 700MB.
  - The exercise is performed off-camera for half the clip.
  - A patient records six check-ins in one day and none the following week.

DONE WHEN.
  - Demonstration and check-in scrub in sync regardless of source format.
  - Cues are frame-accurate and visible to the patient in context.
  - Uploads complete reliably from a phone on home broadband.
  - Every patient video is behind a short-expiry signed URL.

ARTICLE. Two videos, one timeline, no transcoding pipeline — the rendition is a
URL and the comparison is the product.
